Application credentials
Copy Anchor Link
Create your application through the gated self-service flow in
PartnerHub
, or ask your Otter contact for help when that flow is unavailable. After provisioning finishes and you can open the application, select it in
Developers
and open
Keys
for its OAuth
Client ID
and
client secret
.
Use the Client ID shown on Keys, rather than assuming it is interchangeable with an application identifier. Additional credentials have their own Client IDs. Copy a newly issued secret when it is shown; it cannot be retrieved later. Never commit secrets to source control or expose them in a browser, mobile app, or chat.
Self-service starts with a sandbox application. Check the selected application's environment and store connections before sending traffic; creating an application alone does not grant production readiness or connect a merchant store.

Two common OAuth 2.0 flows:
Flow
When to use
Client credentials
Server-to-server integration — no end-user login. Most partner integrations start here.
Authorization code
A merchant user must authorize your app (for example
organization onboarding
). Starts at
GET /v1/auth/oauth2/authorize
, then exchange the code at
/v1/auth/token
.

Scopes
Copy Anchor Link
Tokens and applications are limited by
scopes
(for example organization or orders scopes). Request only what you need. Missing scope → authorization errors even with a valid token. Scope lists are in the
API reference
.
401 versus 503
Copy Anchor Link
401
— the token is missing, invalid, expired, or revoked. Request a new token before retrying.
503
with a
Retry-After
header — Otter could not validate the token at that moment because of a temporary internal issue. It says nothing about whether the token is valid. Retry the same request with the same token after the number of seconds in
Retry-After
, using backoff if the error repeats.
Verifying webhooks (inbound)
Copy Anchor Link
Otter sends HTTPS
POST
events to URLs you register. Each endpoint has a
secret
and an optional
Authorization
style (Basic, Bearer, legacy HMAC SHA1, or none).
Always
validate the
X-HMAC-SHA256
header (HMAC-SHA256 of the
raw
body with your webhook secret) before trusting the payload — regardless of
Authorization
type.
Do not process webhook bodies without signature validation.

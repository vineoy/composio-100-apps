The Three Authentication Methods in Jira Server REST API v2
The API supports three distinct ways to prove your identity. Each one fits a different puzzle, and knowing the difference is where most people stumble.
Basic Authentication
is the quickest entry point. You send a username and password (or a personal API token if you’re on Jira
Data Center
with token support) encoded in Base64. It’s dead simple for scripts and one-off tests. Here’s a curl example:
curl -u alice.writer:MyPa$$word https://jira.example.com/rest/api/2/issue/DEV-123
But here’s the truth: Basic Auth sends credentials with every request. If you hardcode them into a script, you’re one commit away from a security nightmare. That’s why I recommend pairing it with environment variables or a vault after prototyping.
OAuth 1.0a
is the heavy lifter for marketplace apps and integrations that need fine-grained access without sharing user passwords. Jira Server uses a 3-legged OAuth flow that requires an application link and a dance: request token, user authorization, access token. It’s more complex, but once set up, you get token-based access that you can revoke anytime. The official Jira Server REST API v2 documentation references the
/plugins/servlet/oauth/
endpoints for this.
Cookie-based authentication
works well for browser-based dashboards or internal tools that mimic a user session. You POST credentials to
/rest/auth/1/session
, grab the
JSESSIONID
cookie, and attach it to subsequent calls. Add an
X-Atlassian-Token: no-check
header to skip CSRF checks if you’re not using a real browser. This pattern feels like logging into the UI — handy when you need temporary, session-bound access.

When to Use Which Authentication Pattern
Let me make this practical. Here’s a decision framework I follow:
Is this a one-off data pull or a simple internal notification? Go with Basic Auth, but feed the password from a secure store.
Are you building an app that users will install from the Atlassian Marketplace? OAuth 1.0a is your only friend.
Are you creating a lightweight internal dashboard that needs to act on behalf of a logged-in team lead? Cookie auth with CSRF handling will feel the most natural.
You might be wondering: “Can I just use Basic Auth everywhere?” Technically yes, but any shared script leaks credentials. OAuth gives you that crucial “rotate and sleep” peace of mind. Cookie auth, on the other hand, expires when the session ends, so no lingering secrets.
Three Real-World Authentication Patterns That Actually Work
I’ve boiled down the noise to three battle-tested workflows. Each one solves a concrete scenario you’re likely facing right now.
Pattern 1: Automated Slack Notifier with Basic Auth
Suppose you need a cron job that pulls open high-priority issues and posts them to Slack. I’d use Basic Auth with an environment variable for the password. The script runs behind a firewall, so the risk is minimal if you keep the variable out of version control. Example:
export JIRA_PASS='mysecurepassword'
curl -u reporter@company.com:$JIRA_PASS \
  -H "Content-Type: application/json" \
  "https://jira.example.com/rest/api/2/search?jql=priority=High+AND+status=Open"
The pattern is fast, debuggable, and needs zero extra tokens. But rotate that password regularly.
Pattern 2: OAuth for a Timesheet Plugin
Let’s say you’re building a third-party timesheet add-on. Your customers won’t give you their passwords. Here, you implement the 3-legged OAuth flow. First, register an application link in Jira administration. Then, your plugin exchanges a request token for an access token via
/plugins/servlet/oauth/authorize
and
/plugins/servlet/oauth/access-token
. Once you have the token, store it encrypted and sign every request with the OAuth signature. The user can revoke it from their profile, which gives everyone confidence. This pattern matches the detailed walkthrough in the Jira Server REST API v2 documentation for OAuth.
Pattern 3: Internal Support Dashboard with Cookie Auth
Your support team wants a custom page that lists their assigned tickets without refreshing. I’d build a small internal web app that sends a POST to
/rest/auth/1/session
with the manager’s credentials, picks up the
JSESSIONID
, and then calls
/rest/api/2/search
with that cookie and
X-Atlassian-Token: no-check
. The session is tied to the browser-like cookie, so it expires after logout or timeout. Quick to prototype and doesn’t require an application link.

FAQs About Jira Server REST API v2 Authentication
Can I use Jira Server REST API v2 without authentication?
No. All endpoints require authentication. Even public dashboards are behind a login. If you try an unauthenticated call, you’ll get a 401. The quickest way to start is Basic Auth with a dedicated service account to avoid tying the script to a real person’s credentials.
How do I revoke an API token in Jira Server?
Jira Server’s native Basic Auth doesn’t have a token revocation mechanism — you change the user’s password to invalidate access. If you’re using Jira Data Center with personal access tokens, you can revoke them from the user profile. For OAuth, revoke the application link or the user’s access token. This limitation is one reason why many teams look for simpler token management.
Does Jira Server support OAuth 2.0?
No, the REST API only supports OAuth 1.0a. The official Jira Server REST API v2 documentation confirms this. If you need OAuth 2.0, you’d have to move to Jira Cloud or use an identity provider in front of the server, which adds complexity.
How do I handle CSRF with cookie authentication?
When you use a cookie obtained from
/rest/auth/1/session
, add the header
X-Atlassian-Token: no-check
to bypass CSRF checks. This is safe only for server-to-server calls inside a trusted network. For browser apps, you should extract the Atlassian CSRF token from the cookie and include it properly.
Is Basic Auth over HTTPS secure enough for internal tools?
For low-risk internal automation, yes, as long as you never store the password in plain text. Use a secret manager and restrict network access. But if the script ever leaves your private network, move to token-based or OAuth patterns immediately.

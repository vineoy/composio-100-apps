The Systeme.io API
is the public RESTful API of Systeme.io, an all-in-one online marketing and business platform, that enables programmatic access to selected features including contact and tag management, subscription operations, and indirect triggering of automations through actions such as contact creation or tag assignment.
[1]
[2]
The API follows RESTful conventions for consistent and intuitive interactions, with all requests authenticated via an
X-API-Key
header containing a unique API key generated by the user.
[2]
Users can create up to
three
public API keys per account (as of November 2025) through the Systeme.io dashboard by navigating to profile settings, scrolling to the Public API keys section, and following the creation process, which includes assigning a unique name, optionally setting an expiration date, and immediately copying the token as it is displayed only once.
[3]
[4]
A security email notification is sent upon each key creation.
[3]
Key endpoints support operations such as listing and partially updating contacts (using
PATCH
with
application/merge-patch+json
), creating tags, and other resource management tasks, with the base URL at **
https://api.systeme.io/api**.[](https://developer.systeme.io/reference/api)
The API enforces rate limiting with a shared quota across keys, returning a
429 Too Many Requests
response when exceeded, along with relevant headers indicating remaining capacity and retry timing.
[2]
Actions performed via the API, such as creating a contact or assigning a tag, can trigger predefined automations within Systeme.io, allowing developers to build complex workflows or integrate with external services.
[1]
Detailed endpoint specifications, request formats, and examples are available in the official API reference.
[2]
Overview
Introduction
The
Systeme.io API
is the public API of Systeme.io, an all-in-one online marketing and business platform that integrates tools for building sales funnels, email marketing, website creation, affiliate management, marketing automation, and online courses.
[5]
It provides developers with programmatic access to selected features of the platform in a structured and secure way, serving as a gateway to create new applications, services, or integrations that extend Systeme.io's capabilities to other systems.
[1]
The primary purpose of the API is to enable interaction with core platform elements, particularly contact and tag management (including listing, retrieving, and partially updating contacts, along with creating tags and assigning/removing tags via contact updates), and indirect triggering of automations through actions like contact updates or tag assignment, which can activate predefined workflows such as course enrollments or email campaigns.
[2]
[1]
The API uses public API keys for authentication, with a limit of up to two active keys per account that are passed in request headers to secure access.
[3]
It follows RESTful conventions for requests and responses.
[1]
This design supports efficient programmatic integration, marking a significant expansion of the platform's extensibility for users, partners, and developers.
[1]
Key Features
The
Systeme.io Public API
exposes a carefully selected set of features that enable programmatic interaction with the platform's core functionalities in a transparent and efficient manner.
[1]
Key capabilities center on
contact and tag management
. The API allows developers to list or retrieve contacts with filtering options and update existing contacts. Tag-related operations include creating tags, with assignment possible indirectly through contact updates.
[2]
Additionally, the API supports
indirect triggering of automations
. While it does not directly invoke automations, actions such as updating a contact or assigning a tag can activate predefined workflows within Systeme.io, for example enrolling a contact in an online course or adding them to a marketing campaign.
[1]
These features promote interoperability and integration with external systems. They are accessed via authenticated RESTful requests (detailed in Technical Specifications).
[2]
Development and Documentation
The Systeme.io Public API represents a significant development in the platform's ecosystem, enabling programmatic interoperability by allowing developers to directly interact with core features through a structured RESTful interface.
[1]
Official documentation is hosted at
https://developer.systeme.io/reference/api
, which serves as the primary reference for developers and includes details on authentication, rate limiting, pagination, endpoints, and code examples.
[2]
Additional API reference material is available at
https://api.systeme.io/documentation.[](https://api.systeme.io/documentation)
Authentication
API Key Creation Process
To create a public API key on systeme.io, users must first log in to their account and access the dashboard settings. Click the profile picture in the top-right corner and select
Settings
from the dropdown menu. Scroll down to the
Public API keys
section and click the
Create
button to open the creation popup.
[3]
In the popup, enter a unique name for the API key to facilitate easy identification and management. Optionally, set an expiration date and time by selecting a specific date from the calendar and applying it; leaving the expiration field empty results in an indefinite validity period. Once the details are configured, click
Save
to generate the key.
[3]
Immediately after saving, copy the generated API key token by clicking the
Copy
icon next to it, as the token will not be displayed again and cannot be retrieved later. If the token is not copied at this stage, the key must be deleted and a new one created. As a security measure, systeme.io sends an email notification to the account owner whenever a new public API key is generated. Users can have a maximum of two active API keys at any time.
[3]
Key Limits and Management
Users of the Systeme.io API are limited to a maximum of two public API keys active at any given time per account.
[3]
Each key must be assigned a unique name upon creation to enable straightforward identification and management within the dashboard.
[3]
If the token for a key is lost or not copied immediately after generation, it cannot be viewed again; in such cases, the key must be deleted and a new one created to generate a fresh token.
[3]
Security Notifications and Best Practices
Systeme.io sends an email notification to the account owner as a security measure whenever a new public API key is created, enabling users to monitor for unauthorized key generation activity.
[3]
To minimize security risks, API keys should be used in server-side environments; making API calls from public or client-side code exposes the key and poses a significant security threat, potentially allowing unauthorized access to account resources.
[2]
Assigning a unique name to each API key during creation facilitates identification and management, reducing the chance of confusion or misuse.
[3]
Users can set an expiration date for API keys, which automatically invalidates the key after the specified period.
[3]
Users should treat API keys as sensitive credentials, copying them immediately upon creation since they cannot be retrieved later, and avoid hardcoding them in any publicly accessible code or repositories.
[3]
[2]
Technical Specifications
Base URL and Request Format
The Systeme.io API follows standard RESTful conventions, with all requests directed to the base URL
https://api.systeme.io/api/
.
[2]
Endpoints are appended to this base path (for example,
/tags
for tag operations or
/contacts
for contact management), resulting in full URLs such as
https://api.systeme.io/api/tags
or
https://api.systeme.io/api/contacts
.
[2]
Requests require authentication via the
X-API-Key
header, which must contain the user's public API key obtained from the Systeme.io dashboard. This header is mandatory for every request.
[2]
Most requests and responses use JSON format. The
Content-Type
header should be set to
application/json
for requests with a body (such as POST or PUT operations). For partial updates using the PATCH method, the
Content-Type
header is set to
application/merge-patch+json
to support efficient resource modification.
[2]
Responses are returned in JSON, typically with a consistent structure for collections (including keys such as
items
for the data payload). The API uses the following HTTP methods: GET for retrieval, POST for creation, and PATCH for partial updates.
[2]
For example, a request to create a tag might resemble the following curl command:
curl -X [POST](/page/HTTP) 'https://api.systeme.io/api/tags' \
-H 'Content-Type: application/json' \
-H 'X-API-Key: your_api_key' \
-d '{"name": "NewTagName"}'
Similarly, retrieving contacts uses a GET request with only the authentication header required:
fetch('https://api.systeme.io/api/contacts', {
  headers: {
    'X-API-Key': 'your_api_key'
  }
}).then(response => response.json());
These conventions ensure predictable and consistent interaction across all supported endpoints.
[2]
Rate Limiting
The Systeme.io Public API implements a rate-limiting system to maintain service stability and availability for all users. The request limit is shared across all API keys and tokens associated with a user.
[2]
Responses include the following headers to indicate rate limit status:
X-RateLimit-Limit
: the maximum number of requests allowed within the rate limit window.
X-RateLimit-Remaining
: the number of requests remaining in the current window.
X-RateLimit-Refill
: when the quota will be replenished.
[2]
Exceeding the rate limit results in an HTTP 429 Too Many Requests status code, along with a Retry-After header specifying the number of seconds to wait before making another request.
[2]
Pagination
The
Systeme.io API
employs cursor-based pagination to efficiently handle large collections of resources in list endpoints. This method uses a cursor as a reference point to navigate through datasets, avoiding the inefficiencies of offset-based pagination for large result sets.
[2]
Requests to paginated endpoints support the following query parameters:
startingAfter
: Specifies the ID of the last item from the previous page, setting the cursor position for the next set of results.
limit
: Controls the maximum number of records returned per page, allowing developers to tailor responses to their needs.
order
: Determines the sorting direction, with options
asc
(ascending) or
desc
(descending); the default is
desc
.
The response structure includes an
items
key containing the retrieved resources and a
hasMore
boolean field indicating whether additional pages of data remain available. This structure enables clients to fetch subsequent pages by using the ID of the last item in the current response as the
startingAfter
value in the next request.
[2]
This pagination mechanism applies generally to list endpoints that return collections, ensuring scalable and predictable data retrieval across the API.
[2]
Error Handling
The Systeme.io API adheres to RESTful conventions and uses standard HTTP status codes to indicate the outcome of requests, including errors when a request cannot be processed successfully.
Error responses for rate limiting occur when too many requests are sent within a given time frame. In such cases, the API returns a 429 Too Many Requests status code, along with a Retry-After header that specifies the number of seconds to wait before making another request.
[2]
Developers are advised to implement appropriate error handling strategies to manage these responses effectively.
[2]
For comprehensive details on rate limiting, including related headers, see the Rate Limiting section.
While the official documentation focuses primarily on rate limit errors, the API follows common REST practices for other error conditions, returning appropriate HTTP status codes (such as those in the 4xx client error range for invalid requests or authentication issues) to convey specific failure reasons.
API Endpoints
Contact Management
The Systeme.io public API provides endpoints for managing contacts, enabling programmatic creation, retrieval, updating, and deletion of contact records. These operations form a core part of the platform's contact and tag management capabilities, with actions like contact creation or updates potentially triggering configured automations such as course enrollments or campaign additions.
[1]
All requests are sent to the base URL
https://api.systeme.io/api
and require authentication via the
X-API-Key
header containing a valid public API key.
[2]
The GET
/api/contacts
endpoint retrieves a paginated list of contacts, supporting cursor-based pagination through parameters including
startingAfter
(ID of the last item from the previous page),
limit
(number of records per page), and
order
(asc or desc, defaulting to desc). The response returns an object with an
items
array containing contact details and a
hasMore
boolean to indicate availability of additional pages.
[2]
[1]
Individual contacts can be retrieved, updated, or deleted using endpoints such as GET
/api/contacts/{contact_id}
, PATCH
/api/contacts/{contact_id}
, and DELETE
/api/contacts/{contact_id}
. The PATCH method uses the
application/merge-patch+json
content type for partial updates. Standard fields like
locale
are modified directly as top-level properties, while custom fields are updated via a
fields
array of objects specifying
slug
(field identifier) and
value
(new value or
null
to remove).
[2]
New contacts are created via the corresponding creation endpoint, with full details on required body parameters and response formats available in the official API documentation.
[1]
Tag Management
The Systeme.io API supports tag management as part of its contact and tag operations, enabling the creation of tags and their association with contacts to organize audiences and trigger automations. Tags serve as labels that can be applied to contacts for segmentation and workflow automation.
[1]
New tags are created by sending a POST request to
https://api.systeme.io/api/tags
. Requests require authentication using the X-API-Key header and a JSON body specifying the tag name.
[2]
An example using curl:
curl -X [POST](/page/HTTP) 'https://api.systeme.io/api/tags' \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: your_api_key' \
  -d '{"name": "NewTagName"}'
This creates a tag with the specified name.
[2]
The API facilitates assigning tags to contacts, listing tags (including those associated with specific contacts), and removing tags from contacts. These operations are performed through relevant contact endpoints and can trigger automations defined in systeme.io when a tag is assigned.
[1]
For listing tags, pagination may apply as detailed in the Pagination section. Refer to the official documentation for full endpoint parameters, request/response formats, and additional tag-related operations.
[2]
Subscription Operations
The Systeme.io public API does not currently include documented endpoints for dedicated subscription operations in the official API reference (
https://developer.systeme.io/reference/api
).
While a help article mentions capabilities for retrieving subscription resources and performing unsubscriptions (including options for immediate or end-of-billing-cycle cancellation), these are not reflected in the available developer documentation, which primarily covers contacts, tags, and community resources.
[1]
A feature request for customer plan management endpoints exists on the Systeme.io roadmap, suggesting potential future support.
[6]
For the most accurate and up-to-date information on available endpoints, consult the official API reference at
https://developer.systeme.io/reference/api
.
Automation Triggers
The Systeme.io Public API does not provide any direct endpoint for triggering automations. Instead, automations are initiated indirectly as side effects of other API actions, primarily creating or updating contacts and assigning tags.
[1]
When a contact is created or updated via the API, or when a tag is assigned to a contact, these operations can activate predefined automation rules configured within the Systeme.io platform. For example, creating a new contact might trigger an automation that enrolls them in a course or adds them to an email campaign, enabling complex, automated workflows in response to programmatic actions.
[1]
This indirect approach means the API offers no mechanism for directly starting, stopping, or controlling automations, relying instead on existing platform workflows that monitor these specific events.
[1]

MCP for WooCommerce
MCP for WooCommerce
by
w7s
connects
Claude
,
ChatGPT
, and other AI assistants to your WooCommerce store so they can work with your orders, products, customers, and more in plain language. It runs its own Model Context Protocol (MCP) server on the free MCP Adapter plugin, gives you a settings screen to manage the connection and your API keys, and lets you choose exactly which groups of tools the AI client is allowed to use. This guide covers what you need, how to set it up, what every setting does, and how developers can extend it.
MCP for WooCommerce gives your store its own MCP server. MCP is the standard that lets an AI assistant call tools on your site. The plugin’s server lives at
/wp-json/w7s-mcp/v1/mcp
and runs on the MCP Adapter, a free plugin from WordPress.org that handles the MCP protocol for WordPress.
It does three main things:
It provides a settings area under
WooCommerce > Settings > MCP
for connecting an assistant, creating API keys, and reviewing activity;
It registers a large set of MCP abilities so an assistant can list and manage orders, products, customers, coupons, refunds, tax, shipping, webhooks, reports, and more; and
It lets you switch whole groups of tools (called tool packs) on or off, so an assistant only ever sees the capabilities you have chosen to expose.
On top of the server, the plugin adds the connection and key management screens, a large library of abilities, tool pack gating that is enforced when a tool runs, optional activity logging and change history, and API key permission enforcement on every call. It does not depend on WooCommerce’s own MCP feature, which WooCommerce removes in version 11.3.
MCP for WooCommerce needs the following to run:
WordPress 6.9 or higher, which provides the Abilities API.
WooCommerce 10.4 or higher. WooCommerce is a hard dependency. The plugin declares
Requires Plugins: woocommerce
and will prompt you if WooCommerce is missing.
The free
MCP Adapter
plugin, on WooCommerce 11.3 and later, or on any store where no other plugin brings a copy of the adapter. See
The MCP Adapter
below.
PHP 7.4 or higher.
MySQL 5.6 or higher, or the MariaDB equivalent.
An AI assistant that understands MCP, such as Claude, ChatGPT, Cursor, or VS Code with GitHub Copilot, or any other MCP or OpenAPI 3.1 client (Cline, n8n, Ollama, and more).
For Claude.ai in the browser or ChatGPT, an account or plan on the assistant’s side that allows custom connectors, custom GPTs, or MCP servers.
For the one-click Claude Desktop setup: Claude Desktop 0.13.37 or newer, and Node.js 18 or newer on that computer.
Remote connectors use Streamable HTTP. A client can optionally open an SSE stream for server messages; each open stream can occupy a PHP worker for up to an hour before reconnecting. The session itself is stored between requests and does not require a continuously occupied worker. Its idle lifetime is separate and defaults to 24 hours.
WooCommerce 11.2 and earlier bring their own copy of the MCP Adapter, and so do some other plugins, such as Elementor. MCP for WooCommerce works on those copies. WooCommerce stops bringing its copy in WooCommerce 11.3, so installing the MCP Adapter plugin keeps your connections working through that update.

Once MCP for WooCommerce is active, install the MCP Adapter if the plugin asks for it. A notice at the top of your WP Admin dashboard (WordPress Admin dashboard) tells you whether you need it, and offers a button that installs and activates it for you in one click.
The MCP Adapter is a free plugin from WordPress.org. It handles the MCP protocol for WordPress, and MCP for WooCommerce runs its server on it. Without an adapter on the site, no AI assistant can connect to your store.
WordPress and WooCommerce now connect AI assistants through the MCP Adapter plugin. Up to WooCommerce 11.2, WooCommerce brought its own copy of the adapter and its own MCP endpoint, and earlier versions of MCP for WooCommerce connected through them. From WooCommerce 11.3, WooCommerce removes both, and AI connections run through the MCP Adapter plugin instead. MCP for WooCommerce 2.0.0 adapts to that change: it runs its own MCP server on whichever adapter is loaded, so your keys, connector URLs, and configurations keep working.
You need to install the plugin when:
your store runs WooCommerce 11.3 or later, which no longer brings its own copy; or
no other plugin on your site brings a copy of the adapter.
On WooCommerce 11.2 and earlier, MCP for WooCommerce works without the plugin, using the copy that comes with WooCommerce. It still recommends installing the plugin now, so your connections keep working when WooCommerce 11.3 removes that copy.
The MCP Adapter is recommended rather than required, so WordPress never blocks MCP for WooCommerce from activating or updating because the adapter is missing. Instead, the plugin tells you when you need it.

Version 2.0.0 moves MCP for WooCommerce from WooCommerce’s MCP endpoint to its own MCP server, because WooCommerce 11.3 and later remove that endpoint. This section explains what changes for a store that was connected before 2.0.0.
Nothing, apart from installing the MCP Adapter if the plugin asks for it. You do not need to create a new API key, add a connector again, or edit a configuration file:
Claude.ai connectors and ChatGPT apps keep their connector URLs and tokens.
Claude Desktop bundles and configuration files, Cursor, VS Code, n8n, and other clients keep the address and API key they already have.
The nine core product and order tools keep their names, so saved prompts and workflows still find them.
Your Tool Packs choices, API keys, logs, and change history stay as they are.
If your store runs WooCommerce 11.3 or later and no adapter is loaded, assistants cannot connect until you install the MCP Adapter. Once it is active, they work again from their saved settings. On WooCommerce 11.2 and earlier, 2.0.0 shows a warning instead, so you can install it before WooCommerce 11.3 arrives.
New setups use the plugin’s own endpoint,
/wp-json/w7s-mcp/v1/mcp
. The Connection tab, the Claude Desktop bundle, and the copied configurations all point there.
The old address,
/wp-json/woocommerce/mcp
, keeps working for configurations made before 2.0.0. When a request to it carries an API key in the
X-MCP-API-Key
header, MCP for WooCommerce answers it, on every supported WooCommerce version, including 11.3. A future release will retire the old address once stores no longer use it.
WooCommerce > Status
counts the requests that still arrive there, so you can see whether anything still relies on it.
On WooCommerce 11.3 and later, WooCommerce shows its own notice saying its MCP endpoint was removed, and advises moving to the MCP Adapter’s default server with a WordPress Application Password. That advice is for stores that used WooCommerce’s endpoint directly. It does not apply to MCP for WooCommerce, and you do not need to follow it.
Once the MCP Adapter is active and MCP for WooCommerce’s server answers, WooCommerce’s notice is retired. On WooCommerce 11.3 and later, the Connection tab keeps a short note in its place: “WooCommerce 11.3 moved AI connections to the MCP Adapter plugin. MCP for WooCommerce connects through it, so your existing AI connections keep working.” That happens when site readiness runs and passes. As an administrator, go to
WooCommerce > Settings > MCP > Advanced
and select
Verify site readiness
(or
Check again

MCP for WooCommerce keeps using WooCommerce REST API keys, as it always has:
They can be read-only.
A read key cannot change anything in your store. An Application Password carries every permission of the user it belongs to, and has no read-only option.
Each person can have their own.
Every key can be revoked on its own, and the action log records who used which one.
Your existing connections already use them.
Moving to Application Passwords would make every store reconnect every assistant.
The plugin’s MCP endpoints do not accept Application Passwords or a browser login.
The nine core product and order tools keep their names.
They are

WooCommerce’s built-in abilities are an optional pack.
WooCommerce 10.9 and later register product and order abilities of their own. They overlap with the core tools, so they are off by default. You can turn them on in the
WooCommerce built-in abilities

The screenshots of the Connection tab in this guide were taken on a local test site, so their steps start with
Select your environment

The Connection tab is where you link an assistant to your store. It opens with the MCP Adapter status and the connector switch, followed by numbered steps:
MCP Adapter status.
Shown only when the adapter needs attention: what is wrong and the button to fix it. See
The MCP Adapter
.
WooCommerce 11.3 note.
On WooCommerce 11.3 and later, while an adapter is loaded, a line under the status reads: “WooCommerce 11.3 moved AI connections to the MCP Adapter plugin. MCP for WooCommerce connects through it, so your existing AI connections keep working.”, with a
Why this changed
link.
Enable MCP for WooCommerce connector.
The master switch for the whole integration. When it is off, no tools and no keys are exposed to any assistant, and the Tool Packs, Add tools, Store Control, and Activity tabs are hidden. Changes to this switch are saved immediately.
With the connector on, the steps are:
Select your environment
(local sites only) — choose between a public website (accessible on the internet) and a local website (on your computer). On a public site this step is skipped.
Select your AI assistant
— choose
Claude (Recommended)
,
ChatGPT / Codex
,
Cursor
,
VS Code / GitHub Copilot
, or
Other AI service
.
Create an API key
— give the key a description, pick its permission (Read, Write, or Read/Write), and select
Create API Key
. The consumer key and secret are shown once, so save them straight away. The first time you create a key that can write, the plugin asks you to confirm that you understand what an assistant can do with it.
Connect
— follow the instructions for the assistant you chose. They appear once you have created a key, grouped by method in tabs:
One click
,
Prompt
,
MCPB bundle
(Claude only), and
Manual
. Only the methods that work for your assistant and environment are shown. The exact steps are covered in
Connecting an assistant

Under the connect step, the plugin watches for the new key’s first authenticated use. It shows
Waiting for Claude to connect
(or your app’s name) while you follow the steps, then
Connected
when the key has been used. If nothing arrives for a while, it suggests checking that the app finished its setup, with a
Check again

The Advanced tab holds the settings you rarely need while connecting for the first time: logging, how long Claude connector sessions are kept, site readiness, and the API key list. It is always shown, even with the connector off, so you can check your site before you switch it on.
Logging.
These settings are shown while the connector is on:
Log AI assistant actions
records MCP tool calls. It is on by default.
Keep logs for (days)
sets how long entries are kept, from 1 to 365. The default is 7 days, after which entries are deleted automatically.
Redact customer personal data in logs
masks emails, addresses, phone numbers, and similar fields before they are stored. It is on by default.
Record what AI assistants change
keeps the before and after values of everything an assistant changes, encrypted, so you can review and undo it. It is on by default.
Keep change history for (days)
sets how long changes are kept, from 1 to 365. The default is 30 days.
Save these with the
Save Changes
button at the bottom of the tab. See
Activity
for what gets recorded.
Claude connector.
Shown while the connector is on.
Keep Claude connector sessions for
sets how long a session on the remote connector URL can remain idle: 1 hour, 8 hours, or 24 hours. The default is 24 hours. Every message starts the wait again, so this is the longest break a session can take, not its maximum total lifetime. This setting applies to clients using the connector URL; the Claude Desktop MCPB bridge uses a separate adapter session.
After a longer break, Claude starts a new session by itself, but a chat that was already open may not show the store’s tools again. Start a new chat to get them back. A shorter window ends idle sessions sooner. A session only works for the API key or connector URL that started it, and the stored session holds no key, so a longer window does not leave a usable credential in your database. Save it with
Save Changes
.
Site readiness.
Site readiness checks what your store can do and reports it for each AI service separately, so a store that is fine for ChatGPT and blocked for Claude reads as exactly that. The tab shows the last report, with when it ran. Select
Verify site readiness
to run it for the first time, or
Check again
for a fresh one.
The report opens with the overall result and groups the checks beneath it:
Your site
holds the prerequisites every service shares: the
MCP Adapter
, the
MCP for WooCommerce server
(registered with the tools it should have, and answering at its address), the
MCP for WooCommerce connector
switch,
Encryption for connector URLs
,
This plugin’s REST endpoints
, and
Reachable from the internet
.
One group per service holds the checks only that service can fail:
Claude
(its endpoint, streaming replies, the connector URL, and an OAuth conflict with another plugin),
ChatGPT
(its schema endpoint and import URL),
Cursor
,
VS Code / GitHub Copilot
, and
Other AI services
(the MCP endpoint, and whether the app will trust your HTTPS certificate).
Hosting and security
looks for settings that block AI apps: PHP errors printed into responses, a stripped
X-MCP-API-Key
header or
?token=
query string, cached REST replies, a CDN or firewall in front of the site, security plugins, and other MCP plugins. The
Other MCP plugins
row names the MCP Adapter separately, as required: the plugin’s server runs on it, and the adapter’s own default server is a separate address that does not list this plugin’s tools.
Each row carries a Pass, Warning, Fail, or Not checked result, and anything that is not a pass explains itself in place. Each group is collapsed until you open it.
One caveat matters when you read a passing report. Every check runs from your site to itself, so none of them can see a firewall, a staging password, or an AI bot rule sitting between an assistant’s servers and your store. A pass means nothing on your side is in the way. Only a real connection proves an assistant can reach you.
Site readiness also runs as a test under
Tools > Site Health
. Opening that screen runs a fresh check, which also updates the report on the Advanced tab, and the MCP details are on the Site Health
Info
tab. WordPress’s weekly background Site Health check leaves this test out, so it only runs when someone opens the Site Health screen.
Manage API Keys.
The WooCommerce REST API keys an assistant uses, with each key’s description, masked key, permission, and user. A client sends its key in the
X-MCP-API-Key
header. The key’s own permission controls what the assistant can do: a read key can only run read operations like search, list, and get, while write or read/write keys can also create, update, and delete. The user attached to the key must also have the
manage_woocommerce
capability. Create the most limited key that still does the job. Revoking a key from this list immediately cuts off any assistant that was using it — this is also how you disconnect an assistant.
Actions menu.
Every key in the list has an
Actions
menu, opened from the button at the end of its row. It holds everything that key can do:
Copy MCP connector URL (Claude, ChatGPT app)
and
Copy schema URL (Custom GPT)
— the key’s connector URL, in the form the client expects. One key works with every assistant, so both are always offered: the same token authenticates both addresses, and only the endpoint they point at differs. Claude and the ChatGPT app both take the MCP connector URL; only a Custom GPT wants the schema URL. The URL is available whenever you come back, so losing it is not a reason to create anything new.
Regenerate URL
— issue a fresh URL for that key. The previous one stops working immediately, so anyone using it is disconnected until you give them the new one. Every other key, and anyone using it, is unaffected. The confirmation that follows includes copy buttons so you can hand the new URL straight to the assistant.
Disconnect URL
— switch off that key’s URL while the key itself keeps working for clients that send it as a header, such as the Claude Desktop app.
Revoke key
— delete the API key outright. This cannot be undone, and it removes the connector URL with it.
A key that has no connector URL simply shows fewer entries: only
Revoke key
. The Connection tab creates the URL while the newly issued full credential is available. The key list cannot recover that credential later to create a missing URL. To give someone their own URL through this screen, create a new API key in the connection steps.
Developer note: The remote connector for Claude and ChatGPT has to replay an API key to the site on every request, so that credential is stored in your database — one entry per key that has a connector URL. Each entry is encrypted at rest using a key derived from your site’s WordPress salts, which live in
wp-config.php
rather than the database, so a database backup alone does not expose a usable key. Treat each one as a live credential. To revoke a connector, either use
Disconnect URL
in that key’s
Actions
menu, which removes only that URL, or
Revoke key
in the same menu, which removes both. Deactivating the plugin clears every stored connector credential.
Stores that connected before connector URLs became per-key have one older, shared URL that is not tied to a single API key. It keeps working exactly as before, and nothing needs to be changed or re-pasted. It is shown under the API keys list as
Shared connector URL
, where you can copy it or turn it off once everyone using it has their own URL.
This section walks you from a fresh install to a working connection. Which steps you follow depends on two things: the assistant you are connecting, and where your store runs (a public website on the internet, or a local site on your own computer). Read the prerequisites first, then jump to the section that matches your setup:
Connect the Claude Desktop app to a public site
Connect the Claude Desktop app to a local site
Connect Claude.ai in the browser to a public site
Giving each person their own connection
Connect the ChatGPT app to a public site
Connect a Custom GPT to a public site
Connect a Custom GPT to a local site
Connect Cursor or VS Code
Connect another AI service
All of these start the same way. Go to
WooCommerce > Settings > MCP > Connection
, make sure the MCP Adapter status shows no error, pick your environment (on a local site) and assistant, and create an API key. The key is shown once and is the credential the assistant uses. Create the most limited key that does the job: a read key for reporting, a write or read/write key only when the assistant needs to make changes.
Every assistant has a
Prompt
tab in the connect step. It holds a setup prompt with your store’s address, your new API key, and the setup steps for that app. Copy it into the app you are connecting. An app that can change its own configuration, such as Claude Code, can apply it for you; otherwise, the prompt gives you the manual steps to follow.
For Claude, one prompt covers Claude Code, the Claude Desktop app, and Claude.ai in the browser, and the app you paste it into uses the method it supports. The prompt asks the app to check that it reached the right store before it reads any products.
The prompt includes your API key, so treat it like the key itself. It is only available right after you create a key: on a later visit, create a new key to get a prompt.
A few things need to be true before a connection will work. Most failed setups trace back to one of these.
For a public website (your live store on the internet):
The MCP Adapter is active, or the Connection tab shows no error about it.
The site must be reachable over HTTPS with a valid, trusted SSL certificate. A self-signed or expired certificate will fail.
Your host, firewall, or CDN must pass the connector’s POST requests and session headers. If the client opens an optional SSE stream for server messages, streaming responses must also be allowed. A stream can stay open for up to an hour before reconnecting; that is separate from the session’s 24-hour default idle lifetime.
Your host, firewall, or CDN must also let the assistant’s own requests through to
/wp-json/w7s-mcp/
, and to
/wp-json/woocommerce/mcp
if you have configurations from before 2.0.0. Cloudflare and several hosting panels now ship a one-click setting that blocks AI bots, and it blocks the assistant you connected on purpose along with the crawlers you wanted to keep out. See
Requests blocked by Cloudflare or your host
.
Your assistant account or workspace must allow the connection method you choose. Plan availability, administrative permissions, and menu names can change; check the assistant’s current setup requirements.
For a local website (running on your own computer, for example in a tool like Local, MAMP, or Docker):
Connecting locally is more involved and is aimed at developers comfortable with a terminal, with editing configuration files, and with a tunneling tool such as ngrok.
On a local site, the Connection tab starts with an environment picker. Choose
Local website (on your computer)
in Step 1 and the instructions adapt to the local setup, including the extra certificate settings.
Claude Desktop can talk to a local site directly through a bridge, with one extra setting for the local SSL certificates. See
Connect the Claude Desktop app to a local site
below.
Hosted remote connectors, including Claude.ai and hosted ChatGPT connections, cannot reach a private
localhost
address. Expose the site or bridge through a tunnel for those routes. A desktop or CLI MCP client running locally can use your local network instead. See the local Custom GPT steps below for the route the Connection tab offers.
Developer note: The plugin’s manual Claude Desktop instructions use Node.js 22 or newer and recommend its full
npx
path. A Node version or PATH problem is one possible startup failure; check the client’s error rather than assuming it is the cause whenever tools are missing. See the manual setup steps below.
It helps to know what the pieces are before you wire them together.
The MCP endpoint is the address an assistant connects to. MCP for WooCommerce serves it at
/wp-json/w7s-mcp/v1/mcp
. This is the value a bridge needs as its
WP_API_URL
. Pass the full endpoint, not just your site root. Passing only the root returns a
404 rest_no_route
error. Configurations made before 2.0.0 use
/wp-json/woocommerce/mcp
, which keeps working.
The API key authenticates each request. It is a WooCommerce REST API key in the form
consumer_key:consumer_secret
, sent in the
X-MCP-API-Key
header. The key’s permission scope is enforced on every call, so a read key cannot write no matter how a request is phrased. The user attached to the key also needs the
manage_woocommerce
capability.
From there, clients connect in one of three shapes:
A local bridge.
Claude Desktop runs a small helper on your machine that speaks to your store and presents the tools to the app. With the one-click bundle, the bridge ships inside the bundle; with the manual setup, it is the
@automattic/mcp-wordpress-remote
package. The bridge reads the key from its local configuration and sends it as a header. Creating a connector URL also stores an encrypted replayable copy on the site, even if you ultimately use the Desktop bridge; see
Manage API Keys
.
A remote connector.
Hosted clients connect to the Claude-compatible route using Streamable HTTP, with JSON replies to POST requests and an optional SSE stream for server messages. The generated connector URL carries a revocable token instead of the raw API key. Each URL belongs to one API key, whose credential is stored on the site encrypted at rest so the proxy can authenticate its internal requests. A read-only key stays read-only through the connector.
A direct MCP or OpenAPI client.
Tools such as Cursor, VS Code, Cline, n8n, or your own integration talk to the MCP endpoint directly with the
X-MCP-API-Key
header, or import the OpenAPI 3.1 schema. See
Connect another AI service
.

Claude.ai connects through a remote custom connector using Streamable HTTP. It needs a publicly reachable HTTPS address and an account or workspace that permits custom connectors. Remote connectors originate from Anthropic’s servers, including when you use a remote connector in Claude Desktop. The MCPB bundle and local Desktop configuration use a different, local connection path.

X-MCP-API-Key

Because each URL belongs to a single API key, several people can each connect their own Claude.ai account to the same store. See
Giving each person their own connection
.
If more than one person uses an AI assistant with your store, give each of them their own API key rather than sharing one connection. Every key carries its own connector URL, so the people on your team connect independently.
To set someone up, create an API key for them in the connection steps, choose the permission their job needs, and hand them the connector URL that appears with it. Repeat for the next person. Every key keeps its URL in the
Manage API Keys
list on the Advanced tab, in that key’s
Actions
menu, where you can copy, regenerate, or disconnect it later.
Doing it this way rather than sharing one URL gives you three things:
Separate permissions.
A support agent can have a read/write key while a bookkeeper has a read-only one. The permission travels with the URL, so a read-only key cannot make changes no matter how a request is phrased.
A usable audit trail.
The action log uses the key’s description as its user label, falling back to the WordPress user name. Give each key a recognizable description. Keys created in this screen belong to the WordPress user creating them; handing a key to a teammate does not create a separate WordPress account.
Individual revocation.
When someone leaves, revoke their key. Their connection stops and nobody else is interrupted. Regenerating one person’s URL is equally contained.
Anyone can paste the same URL into more than one place if they want to, and a URL is not tied to a particular Claude.ai account — treat it as a credential belonging to the key it came from.

A hosted Custom GPT cannot reach a private
localhost
address, so this route runs the plugin’s bridge locally and exposes it through a tunnel. This bridge is a small Node server bundled with the plugin, separate from the Claude Desktop bridge. The Connection tab shows these steps for Mac, Windows, and Linux, chosen in the
Operating system
dropdown. For plain-HTTP local WordPress sites, also enable the local transport filter described in
the local Claude steps
.
Open a terminal and change into the plugin folder, for example
wp-content/plugins/w7s-mcp/
.
Check that Node.js 18 or newer is installed with
node --version
. The bridge comes with the plugin, so there is nothing else to install.
Set your endpoint and key, then start the bridge. It listens on port 3333. Leave this window open.
On macOS or Linux:
export W7S_MCP_URL="https://yourstore.local/wp-json/w7s-mcp/v1/mcp"
export W7S_MCP_API_KEY="ck_yourkey:cs_yoursecret"
node bridge/dist/chatgpt-server.mjs
On Windows (PowerShell):
$env:W7S_MCP_URL="https://yourstore.local/wp-json/w7s-mcp/v1/mcp"; $env:W7S_MCP_API_KEY="ck_yourkey:cs_yoursecret"; node bridge/dist/chatgpt-server.mjs
In a second terminal, expose port 3333 with a tunnel. With
ngrok
installed and authenticated, run
ngrok http 3333
and copy the HTTPS URL it shows, for example
https://abc123.ngrok-free.app
.
Stop the bridge in the first terminal with Ctrl+C, then start it again with

set to your tunnel URL so the schema points at the public address:
export W7S_MCP_URL="https://yourstore.local/wp-json/w7s-mcp/v1/mcp"
export W7S_MCP_API_KEY="ck_yourkey:cs_yoursecret"
export BASE_URL="https://abc123.ngrok-free.app"
node bridge/dist/chatgpt-server.mjs
In ChatGPT, create a GPT, add an action, and import the schema from
https://your-tunnel-url/openapi.json
.
The tunnel URL changes each time you restart ngrok on the free plan, so you will re-import the schema when it changes. A bridge started before 2.0.0 with
W7S_MCP_URL
ending in
/wp-json/woocommerce/mcp
keeps working.

For authentication, send your WooCommerce API key as the header
X-MCP-API-Key: ck_xxx:cs_xxx
. The schema and connector URLs carry a revocable token instead of the raw key. Paste them only into trusted clients and treat the token URL as a credential. On the connector and schema addresses, passing

Common issues:
The connection steps are missing, and the Connection tab says “The connection steps appear here once the MCP Adapter plugin is active.” Install or activate the MCP Adapter. See
The MCP Adapter
.
No tools appear, or the server shows as failed in Claude Desktop after a manual setup. Check the client error, Node version and executable path, endpoint, and key. The manual examples use the full path to Node 22’s
npx
. The MCPB bundle avoids configuring that command by hand.
A
404 rest_no_route
error. The
WP_API_URL
is set to your site root instead of the full endpoint. It must end in
/wp-json/w7s-mcp/v1/mcp
(or
/wp-json/woocommerce/mcp
for a configuration made before 2.0.0).
A local connection is refused. Check the client error for an unreachable address, a rejected self-signed certificate, or a plain-HTTP refusal. For plain HTTP use the local transport filter; for a self-signed certificate configure certificate handling in the bridge, as in the local Claude steps. These solve different problems and should stay limited to local development.
A client’s SSE events arrive late or a stream hangs. Check the
Streaming replies to Claude
readiness row. If it warns about buffering or compression, ask your host to disable buffering and response compression for the connector’s SSE responses. Normal JSON replies to POST requests do not require an open SSE stream.
An optional SSE stream can hold a connection and a PHP worker for up to an hour before reconnecting. A stored connector session is separate: its default idle lifetime is 24 hours and it does not reserve a worker between requests.
A token or bundle was exposed. Open the
Manage API Keys
list on the Advanced tab and act on that key alone from its
Actions
menu:
Regenerate URL
replaces it,
Disconnect URL
switches the URL off while the key still works as a header, and
Revoke key
removes both. Everyone else’s connection keeps working. Deactivating the plugin clears every stored connector credential.
Opening a connector URL in a browser shows an explanation rather than connecting. A browser GET without a session is not an MCP connection test. The reply is deliberately identical whether the token is valid, expired, or missing, so it does not establish that authentication or tool execution works.
The connector URL was lost. You do not need a new key. Find the key in the
Manage API Keys
list on the Advanced tab and copy its URL from the
Actions
menu.
The assistant asks for approval but no tool result or action-log entry appears. The connection may have failed before tools/call, even if initialize or tools/list reached WordPress. Check the connector debug log and the client error before attributing it to a firewall. See
Claude lists tools but says the server is not connected
and
Requests blocked by Cloudflare or your host
.
A Claude.ai chat lost the store’s tools after a break. The chat was idle for longer than the Claude connector session window. See
A Claude chat lost the store’s tools after a break
.
Claude.ai refuses to add the connector with an authorization or token error, while ChatGPT and the Claude Desktop app work. Another plugin on the site is publishing an OAuth server that Claude finds first. See
Another plugin publishes an OAuth server for your site
.
A host, CDN or security plugin can block an assistant’s requests before WordPress sees them. Compare the assistant’s failure time with your edge security events and connector debug log. An empty Tool calls log alone does not prove a firewall block: a client that fails during initialization never sends a tool call.
To test access from your own machine, run this using your domain and key:
curl -i -X POST \
  -H "Content-Type: application/json" \
  -H "X-MCP-API-Key: ck_yourkey:cs_yoursecret" \
  -H "User-Agent: ChatGPT-User/1.0; +https://openai.com/bot" \
  -d '{}' \
  https://yourstore.com/wp-json/w7s-mcp/v1/chatgpt/tools/woocommerce-orders-list
A plugin JSON response shows that this test reached WordPress; it does not prove that requests from the assistant’s network will pass. An HTML challenge or block page suggests an edge rule. A JSON authorization error may instead come from WordPress. Repeat the request without the
User-Agent
header to check whether that header affects the result, then confirm the matching rule in your host’s logs. Changing the agent string does not reproduce the assistant’s source IP or runtime.
For Cloudflare, open
Security > Settings
, filter by
Bot traffic
, and review
AI Crawler and Agent access policies
. Agent requests made on a person’s behalf and Training crawlers have separate policies. Review the policy for the assistant you use rather than disabling every AI-related protection. See
Cloudflare’s policy instructions
.
If a WAF rule is responsible, scope an exception to the required
/wp-json/w7s-mcp/
paths and the identified blocking feature. Include
/wp-json/woocommerce/mcp
only if an older configuration still uses it. Skip only the feature or rule that is causing the false positive.
Cloudflare’s Skip options
depend on the feature and plan:
Bot Fight Mode cannot be bypassed with a WAF Skip rule
, while Super Bot Fight Mode supports exceptions. See
Bot Fight Mode limitations

If someone else manages the firewall, provide the failed URL, timestamp, client error and matching security event. The plugin still authenticates each allowed request with its key or connector token.
MCP for WooCommerce’s connector URL uses a revocable token, not OAuth. Other plugins may publish OAuth metadata at
/.well-known/oauth-authorization-server

/.well-known/oauth-protected-resource

Site readiness reports an
OAuth conflict with another plugin

For the generated token URL, choose
No sign in
in Claude’s connector setup and leave OAuth client fields blank. Current Claude versions also support fixed request headers, so the bare connector endpoint with

The Claude Desktop MCPB bridge is an alternative: it sends your key directly from your computer and does not use remote-connector OAuth discovery.
A tool pack is a group of related abilities, such as everything to do with orders or everything to do with products. The Tool Packs tab lists every tool with a toggle, its plugin, and its status, with search, plugin and status filters, and a control in the header that switches every tool matching the current filters on or off. Changes take effect once you press
Save Changes
.
Only enabled packs are exposed to AI clients.
This is the main control for deciding what an assistant can and cannot touch.
A disabled pack is invisible to the assistant, and the restriction is enforced when a tool runs, not just hidden from the tool list, so a disabled pack cannot be called even if an assistant knows its name.
One group is not gated this way: the nine core product and order tools. They list, get, create, update, and delete products, and list, get, create, and update orders, which includes changing an order’s status. They are listed under
WooCommerce Core
with the status
Always on
, have no toggle, and are available whenever the connector is on. The API key’s permission is what limits them, so use a read key when an assistant should not be able to change a product or an order. Their names, such as

What is recorded
While an assistant’s tool call runs, the plugin notes every change it makes through WooCommerce or WordPress, and nothing outside a call:
WooCommerce data
: products and variations, orders, coupons, customers, and, when those extensions are active, subscriptions and bookings.
WordPress data
: posts and pages of any type, categories, tags and other terms, comments and reviews, users, settings (options), and the extra fields (meta) attached to any of these.
Only the fields that changed are kept, with their value before the call and after it. A field set and then changed again in the same call shows its first and last value. A call that only reads, or that fails without changing anything, leaves nothing here. Routine housekeeping such as caches, scheduled tasks and locks is never recorded.
Complete recordings have no badge. Warnings appear only when recording is incomplete or unverified:
Partly recorded
: a tool with known effects the history cannot hold, such as an email sent, a payment refunded, or WooCommerce’s own tables for tax rates and shipping zones. Open Details to see which effects are not recorded.
Not verified
: any other tool, including those from other plugins. What it changed through WooCommerce or WordPress is listed, but it may have done more.
Undoing a change
Undo
puts the fields the call changed back to their values before it. It asks first. If someone has changed one of those fields since, Undo stops and shows the value it would restore beside the current one, and only
Overwrite
replaces it, after asking again. Undoing a new item moves it to the trash, and undoing a move to the trash restores the item.
An undo is a change in its own right: it is listed with “Undo of change #N”, the original change is marked
Undone
, and an undo can itself be undone. Undo runs with your permissions at the time: you need to be able to edit that item yourself, as well as manage WooCommerce. While it restores values, the store sends no emails, takes no payments, moves no stock, and schedules nothing.
If an undo fails, it changes nothing and can be tried again. Rarely, another plugin saves its own work part-way through an undo, so part of it is kept even though the undo failed. Undo then says the item may be partly restored, and that change shows as unavailable to undo: check the item and correct it by hand.
What cannot be undone, and why
Undo is offered only where putting values back is safe. The Undo column states whether undo is available; hover over or focus the information icon beside Unavailable to see the reason:
Permanent deletes.
The item no longer exists to restore; only a move to the trash can be undone.
Refunds, order status changes and payment details.
Changing them back would not reverse the money moved or the emails sent.
Passwords, user roles and security settings
(such as the site address, the admin email, who may register, and payment gateway settings). These are never written back by undo.
Changes that could not be stored whole
: a record cut short because it was very large, or saved without encryption because your server lacks it.
Changes from a call that was not fully recorded
, unless putting that one item back is safe on its own.
The badge rows themselves
, and changes already undone.
Personal data
Change history is stored encrypted in your database, and passwords, API keys and other credentials are never stored at all. Values in the Changes section are hidden as ••••, except a few that are not personal, such as prices, stock and statuses.
Show values
reveals the item name and the full stored values in that change’s details modal, and only to someone who may also view that item. When only the item name is hidden, the control is labeled
Show name
; the Before / After values are already visible. Assistants never see hidden values.
What assistants can see
With the

tool pack on (it is on by default), an assistant can answer questions such as “what did you change on this product last week?” by reading the same history, masked exactly as the Changes section shows it before you select
Show values

If your server cannot encrypt (it lacks PHP’s sodium extension), only those non-personal fields are kept and the rest is left out.
History is kept for 30 days by default and deleted by the same daily job as the log. Change it with

These are real situations a store runs into, and the setup in MCP for WooCommerce that handles each one. Every scenario uses abilities the plugin actually ships. Read them as practical recipes. Pick the few that match how you work and start there.
A note on safety before the scenarios. Two controls do the heavy lifting in almost every setup below. The first is the permission scope on your API key. A read key cannot write, and that is enforced when a tool runs, not just hidden from the assistant’s tool list. The second is Tool Packs. Only the packs you enable are exposed, and a disabled pack will not run even if the assistant tries to call it. You can expand any pack to see its individual abilities and switch off the ones you do not want, so you can keep list, get, and update on while turning delete off. The core product and order tools are the exception: they have no toggle and are always available, so the key’s permission is the only thing limiting them. Most of the safety in these scenarios comes from those two settings.
You start the morning wanting numbers. How many orders shipped yesterday. What sold best this week. Which products are about to run out of stock. You do not want to click through five admin screens, and you definitely do not want a tired 7am mistake changing live data.
Set up a read-only assistant. Create an API key with read permission, then enable the Reports and Analytics Reports packs and leave everything else off — the core order and product tools are always available, and the read key keeps them read-only. Now you can ask in plain English and get an answer pulled straight from the store. The Analytics Reports pack returns summaries, not just rows, so “what was net revenue last month” or “show me my top ten products by sales” comes back as a total, not a spreadsheet you have to add up yourself.
The read key is the point. Even if you phrase something as a command, the assistant cannot change an order, edit a product, or refund a payment. The key is blocked from every write operation the moment a tool runs. You get the answers and none of the risk.
Month-end means revenue, tax collected, refunds, and margin. The usual routine is exporting reports, opening them in a spreadsheet, and reconciling by hand. It takes an afternoon and it is easy to fumble a number.
A read key with the Reports and Analytics Reports packs covers most of this. Ask for the revenue summary for the period, the tax summary, and the refund totals, and you get the aggregates back directly. If you run WooCommerce Cost of Goods Sold, the COGS abilities let you ask for margin on a product or an order, so “what was my gross margin on orders last month” is a question you can answer in chat instead of a formula you have to build.
Keep this assistant read-only. Nothing here needs to write, and a read key means your accountant or bookkeeper can use it without any chance of changing the books while they look at them.
You run an agency. A client wants a seasonal price change across a category, new tags on a product line, and a batch of variations updated before a launch. Doing it by hand in WP Admin is slow and error-prone, and when the client asks what changed, you want a clear answer.
Create a read/write key and enable the catalog packs: Product Variations, Product Attributes, Product Categories, Product Tags, Product Shipping Classes, and Product Reviews. The core product tools are already there. The plugin ships batch abilities for variations, attribute terms, categories, tags, and more, so bulk work that would take an hour of clicking becomes a few instructions. Add Tax Rates or Shipping Zones only if the job touches them, and leave the Customers pack off to avoid exposing separate customer-management tools. The always-on order tools can still read and change orders and their customer details, so this does not restrict a write-capable key to the catalog alone.
Keep action logging and change history on for this one. Changes captured through WordPress and WooCommerce are recorded with the time, the key that made them, and the values before and after; review any incomplete-recording warnings. When the client asks what you did, you have the record, and a change made by mistake can often be undone from the Activity tab. Customer fields in the log are masked by default, so the audit trail does not become a second copy of their data.
Your support lead wants the assistant to pull up an order, read its history, add a note, and handle a refund when one is due. What they do not want is a junior agent, or the assistant itself, deleting an order during a busy shift.
Use a write-capable key and enable the Order Notes pack, plus Refunds if your team handles refunds. Expand each pack and switch off the abilities you do not want:
Delete an order note
and
Delete a refund
can come off while list, get and create remain available. The WooCommerce tool set has no delete-order tool. This limits those note and refund operations, but it does not make the key non-destructive: the always-on core product tools still include product deletion. Review those capabilities before handing out a write-capable key.
Action logging gives you the rest of the comfort. You can see which tools ran and when, so a refund issued at the wrong time is a question you can answer rather than a mystery.
You are launching a promotion next week. That means a coupon, maybe a new shipping zone for a region you are expanding into, the right tax rate for it, and a couple of order emails turned on or off for the campaign. Each of those lives on a different settings screen.
MCP for WooCommerce exposes the configuration side of WooCommerce, not just the data. With a read/write key and the relevant tool packs enabled, you can create a coupon with its restrictions and expiry, add a shipping zone and a method, create a tax rate for a new region, and enable or disable specific transactional emails by ID. You describe what the sale needs and the assistant sets it up across those screens in one go.
Because Tool Packs gate these, you decide how far this reaches. Enable Coupons, Shipping Zones, Tax Rates, and Emails for the launch and leave unrelated packs off. That avoids exposing the separate customer-management tools, but it does not remove the customer details available through the always-on order tools. The core product and order tools stay available regardless, so use a key whose permission matches how much change you want to allow.
You run recurring billing with WooCommerce Subscriptions. The questions that matter are different from a one-off store. Which subscriptions are on hold. Whose renewal just failed. What a particular customer is paying and when their next payment lands.
When WooCommerce Subscriptions is active, its pack appears automatically and the assistant can list and filter subscriptions, read a single one, add a subscription note, and look up the orders tied to a renewal. So “show me subscriptions that failed to renew this week” or “add a note to this subscription that the customer asked to pause” become plain questions. The same extension-aware behavior applies to Bookings and Memberships. The packs only show up when the extension is installed, so you never see tools for features your store does not run.
Match the key to the work. A read key is enough for monitoring renewals. Use a write key only if you want the assistant to add notes or make changes.
Not everyone wants to install and configure a desktop client. Sometimes you just want to ask a question while you are already in the dashboard.

This section is for developers extending or customizing MCP for WooCommerce. Hooks are listed by their exact name; read the referenced source for arguments and timing.
/wp-json/w7s-mcp/v1/mcp
is the plugin’s MCP server (server ID
w7s-mcp
), registered with whichever MCP Adapter is loaded. Tested adapter versions are 0.3 (bundled with WooCommerce up to 11.2), 0.6.1 (bundled with Elementor), and 0.7. Authentication is a WooCommerce REST API key in
X-MCP-API-Key
only; the key’s scope is enforced on the parsed JSON-RPC message, batches included, and the key’s user needs
manage_woocommerce
. Application Passwords and cookie sessions are not accepted. Plain HTTP is refused unless
w7s_mcp_allow_insecure_transport
allows it.
/wp-json/woocommerce/mcp
is kept for configurations made before 2.0.0. A request carrying
X-MCP-API-Key
is handed to the plugin’s server; any other request goes to WooCommerce’s own handler (HTTP 410 from WooCommerce 11.3). The route is added when WooCommerce does not register it. Requests are counted per API key ID for
WooCommerce > Status

includes/class-w7s-mcp-legacy-endpoint.php

/wp-json/w7s-mcp/v1/claude/mcp

/wp-json/w7s-mcp/v1/claude/sse

/wp-json/w7s-mcp/v1/chatgpt/openapi.json

/wp-json/w7s-mcp/v1/chatgpt/tools/<tool>

/wp-json/w7s-mcp/v1/connection/health

The current connector speaks the session-based MCP revisions
2025-11-25
,
2025-06-18
,
2025-03-26
and
2024-11-05
. It echoes a supported proposal and otherwise offers
2025-11-25
. The protocol the proxy negotiates with its upstream adapter is stored separately from the client-facing version.
Initialize:
opens a new connector and upstream session. The HTTP 200 JSON-RPC result contains only
protocolVersion
,
capabilities
and
serverInfo
; it does not embed
tools
or
toolsNextCursor
or fetch the catalogue eagerly. The response supplies
MCP-Session-Id
.
Initialized notification:
a POST without an ID is accepted with HTTP 202 and no JSON-RPC response body. It is not forwarded as an upstream request.
Discovery and execution:
the client requests tools/list and tools/call separately. Tool schemas and annotations are normalized on tools/list.
Optional GET stream:
a client can listen for server messages using
Mcp-Session-Id
, or the legacy
session_id
query parameter. The stream closes after at most 3,600 seconds; closing it does not delete the session. An ordinary browser GET without a session receives HTTP 400 with an explanation.
Session termination:
DELETE with a valid session header returns HTTP 204. An expired or unknown session returns HTTP 404 so the client can initialize again.
Modern discovery probes:
the connector does not implement the stateless
2026-07-28
protocol. A session-less modern request such as server/discover receives HTTP 400 with JSON-RPC
-32600
, allowing a client that supports both eras to fall back to initialize. This is not an advertisement of modern protocol support.
Source:
includes/class-w7s-mcp-claude-sse.php
and
includes/class-w7s-mcp-protocol-version.php
.
w7s_mcp_session_ttl
(filter) sets how long a Claude connector session survives without a message, in seconds. It receives the window chosen on the Advanced tab, 86400 (24 hours) by default. The result is kept between 300 seconds and 30 days. Every message starts the wait again. A session past the MCP Adapter’s own 24-hour inactivity timeout keeps working, because the plugin starts a new adapter session when the adapter rejects the old one. Source:
includes/class-w7s-mcp-claude-sse.php
.
A Claude connector session is stored as a transient named
w7s_mcp_sse_<session id>
. New records hold a keyed hash of the API key, the upstream adapter session, a tool-list revision, and timestamps; they do not retain the credential or queued tool responses. A session opened through a connector URL also records a hash of its token. A later request may authenticate with only the session ID while that connector URL remains valid; replacing or removing the URL ends that access. Header-authenticated sessions require the key on every request. Another key receives HTTP 404, as for an expired session. When a legacy record still contains its credential, the loader tries to associate it with a live connector URL before dropping the credential. Session-only access continues if that association succeeds; otherwise the client must supply its credential or start a new session.
w7s_mcp_chatgpt_max_operations
(filter) controls how many operations the Custom GPT schema includes; the default is 30. Values below 1 disable server-side trimming for inspection or another compatible OpenAPI client, but do not change the importing client’s limits or the Tool Packs UI’s Custom GPT selection limit. Source:
includes/class-w7s-mcp-chatgpt-openapi.php
.
w7s_mcp_connector_enabled
(filter) is the master switch returned by
W7S_MCP::is_connector_enabled()

false

includes/class-w7s-mcp.php

Read-only key enforcement relies on two classifiers, both filterable, in
includes/class-w7s-mcp-ability-helper.php
:
w7s_mcp_is_write_operation
decides whether a given ability or tool name counts as a write. The plugin classifies by name (write verbs such as
create
,
update
,
delete
,
batch
; read verbs such as
get
,
list
,
search
). Anything unrecognized defaults to write, so an unknown tool cannot be run by a read-only key. Use this filter to correct the classification for a custom tool.
w7s_mcp_is_destructive_ability
overrides whether an ability is treated as destructive. The plugin first trusts an explicit destructive declaration from the Abilities API, then falls back to name heuristics.
Scope is also checked where each of the plugin’s own abilities runs, in front of its permission callback, so it does not rest on request parsing alone.

W7S_MCP_Readiness_Service

includes/readiness/interface-w7s-mcp-readiness-service.php

get_id()

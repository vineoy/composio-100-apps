Model Context Protocol (MCP)
Copy
Learn how to use the
Model Context Protocol (MCP)
to enable AI agents to securely access and interact with your Intercom data whenever helpful.
Region availability
The Intercom MCP server is available for US and EU hosted workspaces. AU hosted workspaces are not yet supported. Connect using the endpoint that matches your workspace's hosted region — see the connection URLs below.
What is Model Context Protocol?
MCP is a protocol that enables AI tools and applications to connect with Intercom's data and services in a secure, standardized way. It provides a structured method for AI models to:
Find and retrieve Intercom data (conversations, contacts, etc.)
Access specific tools and functionality provided by Intercom
Maintain context about your Intercom workspace when working with AI assistants
How MCP Works
Intercom hosts a remote MCP server that follows the authenticated remote MCP specification (
docs
). This server handles requests from AI tools and provides access to Intercom data through a secure interface.
Connection URLs:
Use the endpoint for your workspace's hosted region. You can tell your region from your workspace URL:
app.intercom.com
is US hosted and
app.eu.intercom.com
is EU hosted.
Region
Streamable HTTP (Recommended)
Legacy SSE (deprecated)
US
https://mcp.intercom.com/mcp
https://mcp.intercom.com/sse
EU
https://mcp.eu.intercom.com/mcp
https://mcp.eu.intercom.com/sse
Requests to the EU endpoint are processed within the EU, in line with Intercom's
Regional Data Hosting
commitments.
When an AI tool or application needs to access Intercom data:
The tool connects to Intercom's MCP server
Authentication verifies the user's permissions
The tool can then access relevant Intercom data and functionality
The connection remains live to receive updates as needed
Benefits of Using MCP
Secure Access
: All data access is authenticated and authorized
Standardized Interface
: Consistent interaction pattern across different AI tools
Contextual Understanding
: AI assistants maintain awareness of your Intercom environment
Increased Development Efficiency
: Retrieve and interpret customer data from Intercom via your internal AI tools to be more efficient in your work

Universal search tool for finding conversations and contacts using a query DSL approach.
Key Features:

Example Queries:

object_type:conversations admin_assignee_id:6

Fin Operator tools
Operator is Fin's internal AI agent. If your workspace has Fin Operator, the Intercom MCP server also lets your AI client ask Operator to do work inside your workspace, read the answers back, and review and apply the changes Operator proposes.
The Fin Operator tools work only when all of the following are true:
Your workspace has Fin Operator.
You connected with OAuth. Bearer token connections do not get the Fin Operator tools.
You can use Operator in Intercom. The tools are authorized as you, so you need the same permission over MCP that you need in the Intercom app.
If you connected with OAuth but your workspace doesn't have Fin Operator, or you don't have permission to use it, the tools can still be listed. Calls to them don't run Operator. Instead,
send_operator_message
returns a short message from Intercom on how to get access, for example by starting a trial, asking an admin, or buying the add-on, and the other four tools say that Operator isn't available yet. The tools start working once you have access.
Connected before the Fin Operator tools were added?
If your OAuth connection was made before the
Use Fin Operator
permission existed, the tools are listed but calls to them return an error asking you to reconnect. Disconnect and reconnect the Intercom MCP server to grant it. Reconnecting also keeps every existing tool working.
There are five Fin Operator tools:
send_operator_message
: send Operator a message; collect the answer later
get_operator_response
: read the latest response from an Operator chat
get_proposal_details
: show what each pending proposal would change. Read-only
apply_proposals
: apply proposals to your workspace's live configuration
reject_proposals
: discard proposals
Only
send_operator_message
uses Operator credits, in the same way as a turn started in Intercom; the other four tools are free.
For parameters, response statuses, tool annotations, a typical workflow, rate limits and troubleshooting, see the
Fin Operator tools guide
.
Setting things up
Authentication Methods
The MCP server supports
two authentication approaches
:
OAuth Flow (Recommended)
: Browser-based authentication with a consent step, described below
Bearer Token
: Direct API token authentication
What to expect during OAuth
When you connect a client with OAuth, your browser shows two screens in order:
The Intercom MCP consent page.
This names the application asking to connect, lists what it will be able to do in your workspace, and shows its Client ID and the address it redirects to after you approve. Choose
Allow
to continue or
Cancel
to stop. Cancel grants nothing.
Intercom's authorization screen.
This asks you to authorize access for Intercom MCP, the server, rather than for the application. After you authorize, you are returned to the application.
Intercom's authorization screen can only name the Intercom MCP server, so the consent page is where you see and confirm which application receives access. The application name is supplied by the application itself and is not verified by Intercom.
Check the redirect address
Before you choose
Allow
, check that the
Redirects to
address belongs to the application you expect. If you did not start the connection yourself, or you do not recognize the application or the redirect address, choose
Cancel
.

Connecting your own MCP client
The providers listed above are already on the allowlist. If you're building your own MCP client, OAuth client registration is automatic — the server supports
Dynamic Client Registration
— but every redirect URI a client registers is checked against an allowlist, which controls where the server will send authorization responses.
What this means for your client:
Bearer token authentication
doesn't use a redirect URI, so there's nothing to request.
OAuth with a callback on
localhost
or
127.0.0.1
is already allowed on any port, so you can develop and test locally right away.
OAuth with any other callback
needs an allowlist entry before the flow will complete.
Until we've added your redirect URI, registration and authorization fail with one of these errors:
Redirect URI https://your-app.example.com/callback is not in the allowlist, reach out to Intercom Customer Support if you believe we should support it
Invalid request: Redirect URI is not allowed
App Store review is a separate approval
Submitting your app for review in the Developer Hub doesn't add its redirect URI to the MCP server allowlist, even though you register the URI there. If your app connects to the MCP server with OAuth, request an allowlist entry as well.
Requesting an allowlist entry
Contact Intercom Customer Support through the Messenger in the bottom right of this page, and include:
The name of your client and what it does with Intercom data
Each redirect URI in full, exactly as your client sends it
The environment each URI serves: development, staging, or production
Your workspace ID
Whether you need a wildcard entry like
https://*.example.com
, and what it needs to cover
We add the narrowest entry that covers your callbacks. For a host you own, that's usually the origin — an entry for
https://app.example.com
covers every path on that host. If your callback runs on a platform shared with other companies, we add the exact path instead, so list every path you use. Wildcards are granted only for domains where you control every subdomain.
One entry covers both
mcp.intercom.com
and
mcp.eu.intercom.com
, so a single request is enough for both regions.

Required Scopes
The Intercom MCP server requires the following permissions to access your workspace data. When using Bearer token authentication, ensure your access token includes these scopes.
Learn more about OAuth permissions
.
Read and list users and companies
: Required for contact and company data access
Read conversations
: Required for conversation data access
Write conversations
: Required for adding internal notes to conversations (add_internal_note)
Read and write articles
: Required for Help Center article access (list, search, get, create, update)
Read audiences
: Required for listing Fin audiences (list_audiences). An OAuth connection authorized before the Intercom MCP integration had this permission must be disconnected and reconnected to get it
Read admins
: Required for Bearer tokens on the tools that act as you: adding internal notes, creating and updating articles, and submitting feedback (add_internal_note, create_article, update_article, submit_mcp_feedback). OAuth connections need nothing extra for it
Use Fin Operator
: Required for the
Fin Operator tools
. Granted through OAuth only; it cannot be added to a Bearer token.
During OAuth, the consent page summarizes these permissions as: view conversations and add internal notes to them, view contacts and companies, view, create and update articles, view Fin audiences, and use Fin Operator. The
Use Fin Operator
permission is requested for every connection, but the tools only work for workspaces that have Fin Operator.
